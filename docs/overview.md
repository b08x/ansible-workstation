# Project Overview: Architecture, Genesis, and Deterministic Convergence

This document describes what the Syncopated workstation repository is, its structural mechanics,
its recursive genesis, and its role as a deterministic gate validator within a multi-agent engineering
ecosystem. For the empirical crucible and codified failure points, see [`failure-points.md`](failure-points.md)
and [`build-process.md`](build-process.md). For day-to-day operations, see [`usage.md`](usage.md).

---

## What This Is

At the functional layer, this repository is an Ansible control repository that converges a
**Fedora 44 / AlmaLinux 10 / Rocky Linux 10** host into a developer workstation across eleven modular roles:

- **System Foundations & Hardening**: System baselines, DNF5 packaging, and CIS L2 hardening (`roles/common`).
- **Low-Latency & Kernel Tuning**: Real-time audio sysctl, cpupower drop-ins, and reboot-safe ZRAM swap allocation (`roles/tuning`).
- **Networking & Virtualization**: NetworkManager baseline profiles (`roles/networking`) and KVM/QEMU virtualization (`roles/libvirt`).
- **Containers**: Isolated runtimes across containerd, nerdctl, and rootless Podman (`roles/containerd`).
- **Desktop Environments**: Seamless GNOME and COSMIC desktop dispatch with seat-aware display manager handlers (`roles/desktop_ui`).
- **Hardware Acceleration**: Optional Intel oneAPI / SYCL and NVIDIA CUDA/CDI vendor stacks (`roles/gpu`).
- **Developer Toolchains & Utilities**: System developer utilities, VS Code, Flatpaks, and input-remapper (`roles/tools`), alongside unprivileged user-space toolchains (`uv`, `bun`, `go`, `cargo`) and firstboot scripts (`roles/user`).
- **Storage & Speech Synthesis**: Multi-protocol storage services (`roles/nas`) and Whisper / Piper local speech pipelines (`roles/tts`).
- **Agent Harnesses**: Provisioning for AI coding agent CLIs: Claude Code, Google Antigravity, Charm Crush, and OpenCode.

Yet the operational output is only half the story. The more significant dimension is the **input, its architectural role, and its recursive origin**.

## The Recursive Multi-Agent Genesis

This repository was not drafted by an architect typing away in isolation. Its origin story is explicitly recursive:
**it was generated by a multi-agent workflow that was generated by a different multi-agent workflow that was generated from sitting down one day and sort of just talking out what sort of automated tools I would personally find useful.**

Through guided context engineering across multiple agentic coding harnesses—including OpenCode, Claude Code,
Antigravity, Charm Crush, and Mistral Vibe—models operated across vanilla configurations, runtime-invoked skills,
persona design, and agentic workflows. Across an estimated **512 recorded sessions** (heuristically tracked
across 46 project lineage entries in the code-insights corpus at an estimated token cost of ~$2,057), stochastic
natural language decoders were granted direct write access to deterministic POSIX system state:

```
[ Conversational Intent ]
          │
          ▼
[ Multi-Agent Tooling & Workflow Generation ]
          │
          ▼
[ Multi-Agent Coding Pipeline (OpenCode, Claude, Antigravity, Crush) ]
          │
          ▼
[ Hardened Ansible Scaffolding & Validation Engine (This Repository) ]
```

At no point did statistical predictors possess an innate understanding of kernel memory limits, systemd unit
lifecycles, or graphical seat boundaries. When asked to tune swap space, models attempted to hot-reload zram
while holding five gigabytes of active swap, triggering `EBUSY` kernel panics. When asked to configure system
services, separate roles fought over configuration files in an endless loop of non-idempotent overwrites.
When asked to restart display targets, models killed active Wayland sessions, severing the operator's terminal.

Across 499 analyzed sessions, the human course-correction rate was **53.1%**. But instead of abandoning
generative methods, every hallucination, permission collision, and premature git commit was treated as an
empirical boundary test. The maintainer converted **22 empirical failure points** into an immutable,
deterministic scaffold:

- Single-ownership invariants that outlaw multi-role file clobbering.
- Sub-second fail-fast precondition assertions (`tasks/assert.yml`) that abort before touching disk state.
- Seat-aware handler queries via `loginctl list-sessions` that prevent desktop termination.
- Strict variable separation between Tier 1 domain SSOT values and Tier 2 role namespaces.

The result is a production operating environment drafted through stochastic generation, stabilized through
human-curated failure lessons, and locked down by deterministic engineering.

## Ansible as Deterministic Gate Validator & Implementer

In this architecture, Ansible is explicitly **not** treated merely as legacy configuration management.
Instead, Ansible serves as the **deterministic execution engine and validation gate** within an agentic pipeline:

1. **Probabilistic Generation vs. Deterministic Execution**: LLM decoders generate probabilistically.
   Even the most capable reasoning models can drift, produce invalid YAML syntax, or invoke undefined module
   parameters. Ansible acts as the deterministic gatekeeper: Abstract Syntax Tree (AST) validation and
   native `argument_spec` validation mechanically enforce correctness before execution.
2. **Sub-Second Pre-Flight Assertion Gates (<1s)**: Every role ships `tasks/assert.yml`, tagged
   `[<role>, assert, always]`. These assertions run in under one second to verify OS distribution, package
   managers (`dnf5`), effective root elevation (`id -u == 0`), hardware capabilities, and user identity
   facts. If an agent proposes a play with invalid assumptions, the gate fails immediately without mutating disk.
3. **Idempotency as a Verifiable Contract**: LLM-generated shell scripts frequently produce side effects on
   successive executions. Ansible enforces declarative desired-state convergence: re-running against a converged
   host produces zero changes (`changed=0`).
4. **Mechanical Boundary Guardrails**: Strict single file ownership and decoupled plays (`local.yml` Play 1 system
   vs Play 2 user) ensure that agent operations cannot bleed into unauthorized filesystem domains.

## Natural Language User Interface (NLUI) & Gherkin-Gated Pipeline

Sitting directly on top of the Ansible deterministic foundation is the **Natural Language User Interface (NLUI)**.
Users describe their intended workstation configuration in high-level natural language:

> *"Configure a bare-metal developer workstation with low-latency audio, NVIDIA CUDA drivers,
> rootless Podman containers, and unprivileged user toolchains for Go and Rust."*

To bridge the gap between open-ended natural language and deterministic execution without hallucination,
the pipeline incorporates **gated step points** structured into formal Gherkin syntax:

```gherkin
Feature: High-Performance Developer Workstation
  Scenario: Provision CUDA acceleration and developer toolchains
    Given an x86_64 Fedora 44 machine with an active NVIDIA GPU (PCI vendor 0x10de)
      And effective UID is 0 (root elevation confirmed)
     When role "gpu" is executed with nvidia_cuda_install: true
      And role "user" is executed for primary user "b08x"
     Then NVIDIA kernel modules (nvidia, nvidia_uvm) must be loaded
      And Negativo 17 repositories must be the sole NVIDIA provider (provider preflight)
      And nvidia-container-toolkit and CDI specification must be configured
      And unprivileged toolchains (~/.local/go, ~/.cargo/bin) must be verified
      And re-running the play must report changed=0
```

### The Multi-Stage Gated Pipeline

```
[ User Natural Language Intent ]
               │
               ▼
[ Step Point 1: NLUI Parsing & Requirement Structuring ]
               │
               ▼
[ Step Point 2: Gherkin Verification Gate ]
  - Explicit Given (Preconditions & Hardware State)
  - Explicit When (Role Execution & Variable Triggers)
  - Explicit Then (Observable Post-State & Zero-Drift Assertions)
               │
               ▼
[ Step Point 3: Deterministic AST & Argument Spec Validation ]
               │
               ▼
[ Step Point 4: Ansible Execution Engine ]
  - Sub-second fail-fast assertions (<1s)
  - Declarative convergence (ansible-playbook / ansible-pull)
```

By placing the Gherkin gate between the NLUI and Ansible, the system guarantees that natural language
requirements are converted into testable behavioral contracts before a single Ansible task compiles or runs.

## Converged Parity: Image Building & Host Convergence

The platform establishes **converged parity across target footprints**. The same Ansible feature sets,
modular roles, and architectural invariants drive two complementary operational pathways:

1. **Declarative Base Image & Appliance Composition (Offline Build)**:
   Integrated with the companion [`osbuild`](https://gitlab.com/syncopatedX/osbuild) repository, the exact
   same logic bakes declarative ISO installers, bootc/OSTree immutable container images, appliance disk images,
   and minimal server foundations.
2. **Active Infrastructure Convergence (Online Execution)**:
   The same roles run against live, running machines—converging physical developer workstations, distributed
   servers, and kiosk appliances to the exact declared specification via `ansible-playbook` or `ansible-pull`.

```
                    ┌─────────────────────────────────────────┐
                    │    Unified Feature Sets & Ansible Roles │
                    │   (common, tuning, networking, gpu...)  │
                    └────────────────────┬────────────────────┘
                                         │
                    ┌────────────────────┴────────────────────┐
                    ▼                                         ▼
    ┌───────────────────────────────┐         ┌───────────────────────────────┐
    │   Declarative Image Building  │         │   Live Host Convergence       │
    │      (companion osbuild)      │         │   (ansible-playbook / pull)   │
    ├───────────────────────────────┤         ├───────────────────────────────┤
    │ - ISO Installer Pipelines     │         │ - Bare-metal Workstations     │
    │ - bootc / OSTree Containers   │         │ - Server Distributions        │
    │ - Appliance & VM Disk Images  │         │ - Kiosk Appliances            │
    └───────────────────────────────┘         └───────────────────────────────┘
```

Because both pathways rely on the identical single-ownership taxonomy and Tier 1 variable hierarchy,
there is zero configuration drift between an ISO baked in CI and an active workstation running in the field.

## Controlled Reference Distilled Dataset

This repository serves as a **controlled reference distilled dataset** for autonomous agents:

- **A Grounded Knowledge Base**: Generative models frequently hallucinate invalid Ansible modules,
  deprecated syntax, or flawed system configurations. This repository provides a vetted, tested, and
  consistent reference corpus demonstrating production-grade patterns.
- **Vetted Architectural Idioms**:
  - *Two-Tier Variable Scoping*: Tier 1 host/domain variables (`user.name`, `intel_oneapi_install`)
    live in inventory without artificial role prefixes; Tier 2 variables (`<role>_*`) remain cleanly
    scoped in role defaults and vars; registered variables are prefixed `_<role>_*`.
  - *Sub-Second Assertions*: Every role includes a standalone `tasks/assert.yml` validating platform,
    elevation, and identity in under one second.
  - *Strict Single Ownership*: Every configuration file on disk is owned by exactly one role.
  - *NVIDIA Provider Mutual Exclusion*: The `gpu` role's preflight fails when more than one NVIDIA
    driver provider (upstream CUDA, negativo17-lts, Negativo 17, RPM Fusion) is configured in
    `/etc/yum.repos.d` (escape hatch `gpu_nvidia_provider_preflight: false`).
  - *Session-Safe Handlers*: Handlers inspect `loginctl list-sessions` to prevent disconnecting active seats.
- **On-Demand Generation**: Autonomous agents can safely reference this dataset to generate custom
  tasks, auxiliary playbooks, or extension roles that immediately conform to the platform's safety contracts.

## Machine Lifecycle & Firstboot Handshake

A fresh workstation moves through three deterministic stages:

```
[ Stage 0: osbuild ]
       │
       ▼ (Kickstart boot to multi-user.target)
[ Stage 1: Console Firstboot (tty1) ]
       │  - Network wait & DNF system upgrade
       │  - sudo ansible-pull -U <repo> --tags system local.yml
       │  - Hardware auto-detection & toolchain installation
       │  - Sets default target: graphical.target
       │  - Drops checkpoint: ~/.initial-firstboot
       ▼ (Reboot to graphical login)
[ Stage 2: Graphical Firstboot (XDG Autostart) ]
       │  - Auto-runs yadm clone --bootstrap (Layer 2)
       │  - Deploys user shell, dotfiles, and editor state
       │  - Drops checkpoint: ~/.local/state/syncopated/firstboot-stage2.done
       ▼
[ Converged Workstation ]
```

1. **Stage 0 (Base Image Composition)**: Built declaratively via companion `osbuild` blueprints into
   bootable ISO appliances or bootc container images.
2. **Stage 1 (System Convergence)**: Boots to `multi-user.target`. Console login on `tty1` executes
   `/usr/local/bin/syncopated-firstboot`, invoking `local.yml` via `ansible-pull`. Drops `~/.initial-firstboot`
   checkpoint to lock Stage 1 against duplicate execution.
3. **Stage 2 (User Dotfile Convergence)**: On graphical login, XDG autostart launches
   `syncopated-firstboot-user.desktop`, prompting dotfile convergence via `yadm clone --bootstrap`.
   Drops `firstboot-stage2.done` upon successful completion.

## Observability & Closed-Loop Telemetry: The llm_analyzer Framework

The repository incorporates an observability and telemetry harness designed to analyze Ansible task
intent and synthesize training datasets:

- **Opt-In Callback Plugin (`plugins/callback/llm_analyzer.py`)**: When enabled via `ansible.cfg`
  (`callbacks_enabled = llm_analyzer`), task execution metadata and YAML are dispatched over a
  background worker pool (`ThreadPoolExecutor`) to an LLM provider, storing structured explanations
  in an append-only trace store.
- **Deterministic Gold Label Recovery (`plugins/callback_utils/llm_metrics.py`)**: Rather than paying
  LLMs to evaluate LLMs, the offline dataset harness utilizes Ansible's native `ModuleArgsParser`.
  Ground truth for 10 of 13 diagnostic fields (module name, FQCN status, parameters, conditions,
  loops, become, delegation, error handling) is extracted deterministically from the AST at zero token
  cost and zero latency.
- **Offline Dataset Generator (`scripts/llm_trainset.py`)**: Transforms captured traces into scored
  DSPy training sets, validating structural accuracy against the deterministic parser baseline.
- **Closed-Loop Feedback**:
  1. *Observe*: Record execution traces and render terminal diagnostics via `rich_ci_formatter`.
  2. *Learn*: Extract deterministic gold labels and compile DSPy training datasets.
  3. *Remediate*: Companion `llmops` runs automated remediation pipelines against empirical failure points.
